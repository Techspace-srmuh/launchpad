# 006 — Club Gmail announcement delivery

Date: 21 November 2026. Status: scoped user-approved direction; implementation and release verification are separate.

The user chose an internally implemented worker sending individual personalized messages through `officialtechspaceclub@gmail.com`, without Apps Script, Brevo, a custom domain or a paid email subscription. Process batches of ten. The user subsequently explicitly removed the proposed 200-recipient daily application limit: **do not impose an application daily recipient cap**. Provider quotas and throttling still apply.

An admin publishes a dashboard notice for all students or event registrants, then previews and queues its separate email. Supported plain-text placeholders are `{name}`, `{event_name}`, `{event_date}` (India time) and `{link}`. Placeholder substitution is not a new selection/approval workflow: “selected” in message text does not change registrations or choose winners. Recipient selection remains the notice's existing audience. There is one email campaign per notice; repeat identical requests are idempotent. New announcements are needed for deliberate reminders.

MAIN holds private queue records, recipient snapshots, attempts and outcomes. A server-only Node.js/Nodemailer worker uses Gmail SMTP and an app password, claiming one job immediately before each send. Database leases coordinate workers. Up to ten messages are attempted per batch, one second apart, with at least one minute between completed batches. These are initial adjustable implementation pacing values, not Gmail capacity guarantees. Gmail's daily-quota responses pause all sending for 24 hours; auth failures pause for an hour. Definite transient rejections back off exponentially and stop after five attempts. Admin retries require an audited reason. Uncertain SMTP acceptance or an interrupted sending lease is never retried automatically; explicit admin review can authorize a retry with duplicate risk.

Acceptance: authorized admins can preview personalized content and queue exactly one job per intended confirmed account; students/anonymous/revoked admins cannot enumerate private queue data or invoke mutations; concurrent queue requests do not duplicate campaigns; overlapping workers cannot claim the same job; retries and quota failures preserve dashboard notices; progress distinguishes Gmail acceptance from inbox delivery.

The worker is an executable process (`npm run email:worker`), with `--once` available for an external scheduler. It does not run inside a browser or an unawaited frontend request. Running it locally requires that computer to remain on; continuous hosted operation still requires a selected and tested Node-capable host or scheduler. No always-on free hosting, Gmail delivery, institutional consent/retention policy, or production readiness is implied. Actual Gmail credentials, a real authorized send and hosted operation remain setup/release checks. The overall specification remains draft.
